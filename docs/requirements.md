# 解説動画生成ツール 要件定義

Oct 3, 2026 · @ganeysa

## 概要・目的

台本を書けば、AIエージェントが解説動画を安定した品質で仕上げられるツールを作る。狙いは、LLMが苦手な2点をツール側で肩代わりすること。

- **出力が見えない**：レンダリング結果をフレーム画像と数値チェックで返し、AIが自分で直せるループを作る
- **時間軸が苦手**：タイミングはナレーション音声の長さから自動で決め、AIには「何を見せるか」だけを書かせる

成功の基準は、1本の解説動画（3〜5分想定）を、手作業でのタイミング調整なしに作れること。

## スコープ

対象は、自分が作る技術・学習系の解説動画。最初は個人利用とし、公開（OSS化）は後で判断する。

| 区分 | 内容 |
| --- | --- |
| 対象 | 図解・箇条書き・コード・数式を中心にした解説動画（16:9、日本語ナレーション付き） |
| 対象 | 既存のMarpスライドからの動画化 |
| 対象 | AIエージェント（Claude Codeなど）からの操作と、人間がCLIで直接操作する場合の両方 |
| 対象外 | 実写素材の編集、アバターや顔出し |
| 対象外 | 音楽同期のMV、凝ったモーショングラフィックス |
| 対象外 | 画像・動画生成AIによる素材生成（必要になれば後で検討） |
| 対象外 | 職場の資料の動画化 |

## 全体パイプライン

```
台本(.md) → ①パース → シーン定義JSON → ②音声生成(VOICEVOX) → ③自動タイミング → timeline.json
  → ④自動検査 → ⑤キーフレーム → (問題あり: AIが台本を直して①へ) → ⑥MP4書き出し
```

人間が書くのは台本だけで、タイミングは音声の長さから自動で決まる。検査で問題が出たらAIが台本かシーン定義を直し、合格するまで回す。

## 機能要件

中核は「部品集」と「レビューループ」の2つ。ここがツールの価値で、残りはつなぎ込み。

| ID | 機能 | 内容 | 優先度 |
| --- | --- | --- | --- |
| F1 | 台本パース | Markdown台本をシーン・ナレーション文・表示要素に分解し、シーン定義JSONにする | MVP |
| F2 | 音声生成 | ナレーション文ごとにTTSで音声を作り、文ごとの秒数をタイミングJSONに書き出す | MVP |
| F3 | 自動タイミング | 表示要素の出現・強調を、対応するナレーション文の開始時刻に合わせる | MVP |
| F4 | 解説部品集 | タイトル、箇条書きの順次表示、コードハイライト、図解（箱と矢印）、強調マーカー、数式、画像表示などの部品 | MVP（3〜4種から） |
| F5 | プレビュー・レンダリング | ブラウザでプレビューし、MP4に書き出す | MVP |
| F6 | 自動検査 | 画面外へのはみ出し、要素の重なり、文字サイズの下限、1画面の情報量、表示時間の短すぎを検出し、テキストで報告する | MVP |
| F7 | ビジュアルレビュー | シーンごとのキーフレームを画像で書き出し、AIに見せて修正させる | MVP |
| F8 | 字幕 | ナレーションから字幕を生成し、焼き込みかSRTで出力する | 第2段階 |
| F9 | BGM・効果音 | BGMの音量をナレーションに合わせて自動で下げる、場面転換の効果音 | 第2段階 |
| F10 | 部分再生成 | 変更したシーンだけ音声・レンダリングをやり直す（キャッシュ） | 第2段階 |
| F11 | Marp変換 | Marpスライドを台本の下書きに変換する（スライド1枚＝1シーン） | 第3段階 |
| F12 | エージェント連携 | 全機能をCLIで提供し、その上に薄いMCPサーバー（または自作Skill）をかぶせる | MVPはCLIのみ |
| F13 | テーマ | 色・フォント・余白をテーマファイルで切り替える | 第2段階 |

## 入力仕様（台本フォーマット案）

台本は人間もAIも書けるMarkdownにする。`##` がシーン、地の文がナレーション、`:::` ブロックが画面に出すもの。`{n}` は「n番目のナレーション文が始まるときに出す」という指定で、秒数は書かない。

```markdown
---
title: DynamoDBのパーティションキー入門
theme: wakaba
voice: zundamon
---

## なぜキー設計が大事か

DynamoDBでは、データの置き場所がキーで決まります。
キーが偏ると、一部のサーバーにアクセスが集中します。

:::bullets
- {1} 置き場所はキーで決まる
- {2} 偏るとホットパーティション
:::

## 悪い例

このコードでは日付をキーにしています。
今日の日付に書き込みが集中してしまいます。

:::code lang=ts highlight="{1}:1 {2}:2"
const item = { pk: today, sk: userId };
await db.put(item);
:::
```

ツール内部では、これを部品名・引数・開始文番号を持つシーン定義JSONに変換する。AIが直接JSONを書く経路も残す。

## 非機能要件

- **ベンダー非依存**：中核はLLMに依存しないCLIとJSON仕様にする。Claude以外のエージェントや手作業でも同じ結果になること
- **自分で理解できる構成**：他人製のSkillやブラックボックスに頼らず、部品・検査ルールは自分で読めるコードで持つ
- **再現性**：同じ台本・同じバージョンなら同じ動画になる（乱数や現在時刻を使わない）
- **速さ**：1シーンの修正からプレビュー確認まで1分以内を目安にする
- **ローカル完結**：TTSとレンダリングは手元のPCで動かせること。クラウドは必須にしない
- **権利**：TTS音声・フォント・BGMは利用規約とクレジット表記の要否を素材ごとに管理する
- **成果物の管理**：台本・シーン定義・テーマはGitで管理し、音声・動画は生成物として除外する

## 技術選定案

第一候補はRemotion＋VOICEVOX＋Playwright。Reactの知識がそのまま使え、部品化と検査を同じTypeScriptで書けるのが決め手。

| 役割 | 第一候補 | 代替案 | 選ぶ理由・懸念 |
| --- | --- | --- | --- |
| 映像エンジン | Remotion | Motion Canvas、Manim | React部品として解説パーツを作れる。数式中心の回だけManimを併用する手もある。ライセンス条件は要確認 |
| 音声合成 | VOICEVOX（ローカルAPI） | クラウドTTS | 無料・ローカルで動く。キャラごとの利用規約とクレジット表記に注意 |
| 検査・キャプチャ | Playwright | Remotionの静止画書き出し | DOMから要素の位置を取れるので、はみ出しや重なりを数値で判定できる |
| 言語・CLI | TypeScript（Node.js） | Go | エンジンと同じ言語でまとめる |
| 数式 | KaTeX | MathJax | 軽くて速い |
| コード表示 | Shiki | Prism | VS Code相当の配色が使える |
| エージェント連携 | 自作MCPサーバー（CLIの薄いラッパー） | 自作Skill | CLIを主にして、どのエージェントからも呼べるようにする |

## フェーズ計画

まず「1シーンが台本から動画になり、AIが自分で直せる」ところまでを最短で通す。部品を増やすのはその後。

1. **フェーズ0：技術検証**
   - Remotionで1シーンを手書きし、VOICEVOXの音声と合わせて書き出す
   - 完了条件：音声の長さに合わせて箇条書きが順に出るMP4ができる
2. **フェーズ1：MVP**
   - F1〜F7（台本パース、音声、自動タイミング、部品3〜4種、レンダリング、自動検査、ビジュアルレビュー）をCLIで実装
   - 完了条件：1〜2分の解説動画を台本だけから作り、AIが検査結果を見て1回以上自力で修正できる
3. **フェーズ2：実用化**
   - 字幕、BGM、部分再生成、テーマ、部品の追加（図解・数式）、MCPサーバー化
   - 完了条件：3〜5分の動画を1本、実際に公開できる品質で作る
4. **フェーズ3：連携・公開**
   - Marpスライドからの変換、部品集のドキュメント化、OSS化の判断
