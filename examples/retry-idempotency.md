APIのリトライと冪等性

## 今日の内容

{face:normal}最初に、失敗した通信をやり直す理由を見るのだ。
次に、やり直しで起きる二重処理の落とし穴を説明するのだ。
最後に、何回やり直しても安全にする方法を紹介するのだ。

:::bullets
- {1} 失敗したらやり直す理由
- {2} 二重処理の落とし穴
- {3} 何回やり直しても安全にする
:::

## 通信は失敗する

{term:クライアント}APIを呼ぶ側をクライアント、処理する側をサーバーと呼ぶのだ。
ネットワーク越しの通信は、ときどき失敗するのだ。
サーバーが混んでいて、応答がなかなか返ってこないこともあるのだ。
{term:タイムアウト}そこで、決めた時間までに応答がなければ失敗とみなすのだ。これをタイムアウトと呼ぶのだ。

:::diagram
- {1} クライアント
-> {2} 要求
- {1} サーバー
:::

:::callout {4}
決めた時間を過ぎたら失敗とみなす
:::

## リトライ

{term:リトライ}失敗した処理をもう一度やり直すことを、リトライと呼ぶのだ。
一時的な失敗なら、少し待ってやり直せばたいてい成功するのだ。
{face:smile}だから、APIを呼ぶ側はリトライするのが普通なのだ。

:::term {1}
リトライ
:::

:::bullets
- {2} 一時的な失敗は、やり直せば成功する
- {3} 呼ぶ側はリトライするのが普通
:::

## 落とし穴

{face:think}ところが、タイムアウトには落とし穴があるのだ。
サーバーでは処理が成功していて、応答だけが届かなかったのかもしれないのだ。
{face:surprised}クライアントからは、処理が失敗したのか成功したのか区別できないのだ。

:::diagram direction=TB
- {1} 要求を送る
->
- {2} サーバーで処理は成功
-> {2} 応答が消える
- {3} クライアントはタイムアウト {!3}
:::

## 二重処理

{face:troubled}このままリトライすると、同じ処理が2回行われてしまうのだ。
たとえば注文のAPIなら、同じ商品を2回注文してしまうのだ。
支払いなら、お金を2回引き落としてしまうのだ。

:::bullets
- {1} 同じ処理が2回行われる
- {2} 注文が2つできる
- {3} 2回引き落とされる {!3}
:::

## 冪等性とは

{face:normal}そこで大事になるのが、冪等性という考え方なのだ。
冪等性は、同じ操作を何回やっても、1回やったときと結果が変わらない性質のことなのだ。
冪等な処理なら、何回リトライしても安全なのだ。

:::term {2}
冪等性
:::

:::callout {3}
冪等な処理は、何回リトライしても安全
:::

## 身近な例

身近な例で考えてみるのだ。
「部屋の明かりをつける」は、何回押しても明かりがついた状態のままなのだ。
{face:troubled}でも「明るさを1段上げる」は、押すたびに明るくなってしまうのだ。

:::bullets
- {2} 明かりをつける → 冪等
- {3} 明るさを1段上げる → 冪等ではない
:::

## HTTPメソッド

{face:normal}{term:HTTPメソッド}APIには、何をしたいかを伝えるHTTPメソッドという種類があるのだ。
GETやPUT、DELETEは、決まりとして冪等に作るのだ。
{face:think}ところが、新しく作るときに使うPOSTは冪等ではないのだ。

:::bullets
- {2} GET・PUT・DELETE → 冪等に作る
- {3} POST → 冪等ではない {!3}
:::

## 冪等キー

{face:normal}POSTを安全にするのが、冪等キーなのだ。
冪等キーは、1回の操作ごとにクライアントが付ける一意のIDなのだ。
サーバーは、同じキーの要求を1回だけ処理するのだ。

:::term {2}
冪等キー
:::

:::diagram
- {1} 注文の要求
-> {2} キー付き
- {3} 処理済みか確認 {!3}
:::

## サーバー側の流れ

サーバー側の流れをコードで見てみるのだ。
まず、そのキーをもう処理したかどうかを調べるのだ。
{face:smile}処理済みなら、前と同じ結果を返すだけなのだ。
まだなら処理をして、キーと結果を保存するのだ。

:::code lang=ts highlight="{2}:2 {3}:3 {4}:4-5"
const key = req.headers["idempotency-key"];
const done = await findResult(key);
if (done) return done;
const result = await createOrder(req.body);
await saveResult(key, result);
return result;
:::

## DynamoDBで作る

{face:normal}{term:DynamoDB}DynamoDBは、AWSのデータベースサービスなのだ。
DynamoDBを使うなら、条件付き書き込みが便利なのだ。
{term:条件付き書き込み}条件付き書き込みは、条件を満たすときだけ書き込むDynamoDBの機能なのだ。
キーがまだ無いときだけ書き込めば、2回目の書き込みは失敗するのだ。

:::code lang=ts {2} highlight="{4}:4"
await db.put({
  TableName: "orders",
  Item: { PK: key, result },
  ConditionExpression: "attribute_not_exists(PK)",
});
:::

## リトライの間隔

{face:think}リトライには、もう一つ工夫があるのだ。
失敗してすぐにやり直すと、混んでいるサーバーをさらに混ませてしまうのだ。
{term:指数バックオフ}そこで、やり直すたびに待ち時間を2倍ずつ長くするのだ。これを指数バックオフと呼ぶのだ。

:::bullets
- {2} すぐやり直す → さらに混む
- {3} 待ち時間を2倍ずつ延ばす {!3}
:::

:::math {3}
\text{待ち時間} = \text{基本の時間} \times 2^{\text{回数}}
:::

## ジッター

{face:normal}{term:ジッター}さらに、待ち時間にランダムなずれを足すのだ。これをジッターと呼ぶのだ。
たくさんのクライアントが、同じ瞬間に一斉にやり直すのを防げるのだ。

:::term {1}
ジッター
:::

:::callout {2}
一斉のやり直しを、ばらけさせる
:::

## まとめ

今日の内容をまとめるのだ。
タイムアウトしても、サーバーでは処理が成功しているかもしれないのだ。
だから、リトライする処理は冪等にするのだ。
POSTには冪等キーを付けて、待ち時間は指数バックオフとジッターでばらけさせるのだ。

:::bullets
- {2} タイムアウトでも成功しているかもしれない
- {3} リトライする処理は冪等に {!3}
- {4} 冪等キー、指数バックオフ、ジッター
:::
