## DynamoDBとは

DynamoDBは、AWSが提供するキーバリュー型のデータベースなのだ。
{term:キーバリュー型}キーバリュー型というのは、キーを指定して値を出し入れする、シンプルな形のことなのだ。
サーバーの管理をしなくても、大量の読み書きをさばけるのが特徴なのだ。
{face:think}ただし、その性能を引き出すにはキーの設計がとても大事なのだ。

:::bullets
- {1} AWSのキーバリュー型データベース
- {3} サーバー管理なしで大量の読み書き
- {4} 性能はキー設計しだい {!4}
:::

## アイテムとキー

{face:normal}{term:アイテム}データの1件をアイテムと呼ぶのだ。
表でいうと、1行にあたるのだ。
アイテムには、必ずキーが付いているのだ。
この例では、ユーザーIDがキーになっているのだ。

:::code lang=json highlight="{3}:2 {4}:2"
{
  "PK": "user#123",
  "name": "ずんだ",
  "plan": "free"
}
:::

## パーティションとは

DynamoDBは、データをたくさんのパーティションに分けて保存するのだ。
パーティションは保存場所の単位で、それぞれが別々に読み書きをさばくのだ。
そして、どのパーティションに置くかを決めるキーを、パーティションキーと呼ぶのだ。

:::term {2}
パーティション
:::

:::term {3}
パーティションキー
:::

## データの置き場所

アイテムを書き込むと、まずパーティションキーからハッシュ値を計算するのだ。
{term:ハッシュ値}ハッシュ値は、キーから計算したばらばらの数値で、同じキーなら必ず同じ値になるのだ。
{face:surprised}そのハッシュ値で、どのパーティションに置くかが決まるのだ。

:::diagram
- {1} アイテム
-> {1} PK
- {1} ハッシュ関数
->
- {3} パーティション {!3}
:::

## 置き場所の計算

{face:normal}計算のイメージは、この式のようになるのだ。
同じキーは、いつも同じパーティションに置かれるのだ。
違うキーなら、パーティション全体にばらけるのだ。

:::math {1}
\text{置き場所} = \mathrm{hash}(\text{PK}) \bmod N
:::

:::bullets
- {2} 同じキー → いつも同じ場所
- {3} 違うキー → 全体にばらける
:::

## 負荷が均等なら

パーティションの数をNとするのだ。
キーがうまくばらければ、1つのパーティションの負荷は全体のN分の1になるのだ。
{face:smile}だから、パーティションを増やすほど速くさばけるのだ。

:::math {2}
\text{1つあたりの負荷} = \frac{\text{全体のリクエスト}}{N}
:::

:::callout {3}
パーティションを増やすほどスケールする
:::

## ホットパーティション

{face:troubled}ところが、キーが偏ると話が変わるのだ。
アクセスが1つのパーティションに集中してしまうのだ。
{term:ホットパーティション}これをホットパーティションと呼ぶのだ。

:::image src=assets/hot-partition.png {2}
パーティションごとのアクセス数（イメージ）
:::

## 何が困るのか

1つのパーティションがさばける量には上限があるのだ。
{face:angry}上限を超えると、リクエストがスロットリングで弾かれるのだ。
{term:スロットリング}スロットリングは、上限を超えたリクエストをエラーにして断ることなのだ。
ほかのパーティションが空いていても、助けてはくれないのだ。

:::bullets
- {1} パーティションごとに上限がある
- {2} 超えるとスロットリング {!3}
- {4} 空いている所は助けてくれない
:::

## 悪い例1 日付

{face:think}よくある失敗は、日付をパーティションキーにすることなのだ。
今日のデータの書き込みは、すべて今日のキーに集まるのだ。
つまり、毎日1つのパーティションに書き込みが集中するのだ。

:::code lang=ts highlight="{1}:2 {3}:2"
const item = {
  PK: "2026-10-03",
  SK: orderId,
};
:::

## 悪い例2 種類が少ない値

ステータスのように、種類が少ない値も危ないのだ。
{face:troubled}値が三つしかなければ、使えるパーティションも三つまでなのだ。

:::code lang=ts highlight="{1}:2"
const item = {
  PK: "status#active",
  SK: userId,
};
:::

:::callout {2}
値の種類が少ないと、使える場所も少ない
:::

## 良い例 ユーザーID

{face:smile}おすすめは、ユーザーIDのように種類が多い値なのだ。
アクセスが多くのユーザーに散らばるので、負荷もばらけるのだ。

:::code lang=ts highlight="{1}:2"
const item = {
  PK: `user#${userId}`,
  SK: orderId,
};
:::

## 良いキーの条件

{face:normal}良いパーティションキーの条件をまとめるのだ。
まず、値の種類がたくさんあること。
次に、アクセスがそれぞれの値に均等にばらけることなのだ。

:::bullets
- {2} 値の種類がたくさんある
- {3} アクセスが均等にばらける
:::

## 書き込みシャーディング

{face:think}どうしても日付で集計したいときは、工夫ができるのだ。
日付の後ろに、0から9までの番号を付けて書き込みを分けるのだ。
{term:シャーディング}このように、1つの値を番号付きの複数のキーに分けることを、シャーディングと呼ぶのだ。
読むときは、10個のキーをまとめて読めばよいのだ。

:::code lang=ts highlight="{2}:1-2 {4}:4"
const shard = hash(orderId) % 10;
const pk = `2026-10-03#${shard}`;
// 読むときは #0 から #9 まで
const pks = range(10).map((i) => `2026-10-03#${i}`);
:::

## ソートキーと組み合わせる

{face:normal}{term:ソートキー}ソートキーは、同じパーティションキーの中で、並び順を決めるキーなのだ。
パーティションキーで場所を分けて、ソートキーで並べるのが基本なのだ。
{face:smile}同じユーザーの注文を、日付順に取り出すことができるのだ。

:::diagram
- {2} PK ユーザーID
-> {2} 場所を決める
- {2} パーティション
-> {2} 並べる
- {2} SK 注文日時 {!3}
:::
